# Dokkebi Framework — AI/Agent Vibe-Coding Guide

> **This document is the core operations manual that AI coding agents (Cursor, Claude Code, Copilot, etc.) must consult when working on Dokkebi framework projects.**
> Without reading this document, you may introduce security vulnerabilities or cause build errors.

---

## 0. What to know first (TL;DR)

### What the Dokkebi framework is

```
"Serverless Client Backend Framework"
Backend code runs in QuickJS WASM inside the browser;
the server only does trust verification + DB proxy.
```

| Area | Where it runs | Role |
|---|---|---|
| Frontend | Browser | UI |
| **Backend business logic** | **QuickJS WASM in browser** | Controllers, business rules |
| Trust boundary (middleware) | Cloudflare Pages Functions or `dok serve` | Auth/authorization, query validation |
| DB proxy | Same as above | D1 / Supabase / Appwrite calls |
| Database | Cloudflare D1 / Supabase / Appwrite | Actual data storage |

### Two deployment modes

```js
// dokkebi.config.js
proxyMode: 'serverless',  // Deploy middleware to Cloudflare Pages Functions (default)
proxyMode: 'server',      // Self-hosted Node.js server (dok serve)
```

### Never forget

> **Business logic in client WASM is not trustworthy.**
> Memory hacking/reversing can tamper with anything.
> **Real security is enforced by server-side middleware**
> (`worker/api/_dokkebi/db.ts`).
> All permission/tenant validation is forced there.

## 1. Project structure

A Dokkebi project is created with `dok create` and has this structure:

```
my-app/
├── dokkebi.config.js     ← Framework config (security, DB, deploy)
├── .env                  ← Credentials (must be in gitignore)
├── package.json
├── wrangler.toml         ← Cloudflare Pages config (serverless mode)
│
├── backend/              ← Runs in QuickJS WASM in browser
│   ├── controllers/      ← Route handlers (router.METHOD)
│   │   └── index.ts      ← Entry point
│   └── models/           ← Table DSL definitions (dokkebi-dsl)
│       └── index.ts
│
├── frontend/             ← Normal SPA (Vue/React/Vanilla)
│   └── src/
│
├── worker/               ← serverless mode — Pages Functions source (TS)
│   ├── _middleware.ts
│   └── api/
│       └── _dokkebi/     ← Auto-generated by framework. Do not edit manually.
│           ├── handshake.ts
│           ├── db.ts
│           └── log.ts
│
├── functions/            ← worker/ → esbuild compile output (auto)
│
└── dist/                 ← Build output (auto)
    └── dokkebi/          ← WASM bundle, allowlist, registry, etc.
```

**Important**:

- `worker/api/_dokkebi/*.ts` files are auto-generated by `dok build`. **Do not edit manually**.
- `functions/` is auto-generated from compiled `worker/`.
- Custom API routes go under `worker/api/` paths other than `_dokkebi`, or mainly as `router.METHOD` handlers in `backend/controllers/`.

## 2. Writing the backend (most important)

Dokkebi backend consists of **`backend/controllers/` and `backend/models/`**.

### 2.1 Model definitions (`backend/models/`)

Declare tables with `dokkebi-dsl` `table()` / `col()` / `t.xxx()`.

```typescript
// backend/models/index.ts
import { table, col, t } from 'dokkebi-dsl';

// Normal table — relies on convention inference (auto-detects user_id)
export const posts = table('posts', {
  id:        col('id',          t.uuid().primaryKey().default('random')),
  userId:    col('user_id',     t.text().notNull()),
  title:     col('title',       t.text().notNull()),
  content:   col('content',     t.text()),
  createdAt: col('created_at',  t.timestamp().default('now')),
});

// Security-critical table — explicit permission/tenant via DSL options
export const premiumContents = table('premium_contents', {
  id:      col('id',      t.uuid().primaryKey()),
  content: col('content', t.text()),
  userId:  col('user_id', t.text()),
}, {
  // Tenant isolation: auto-inject user_id condition in SQL (Tenant Policy)
  tenant: 'user_id',
  // Or detailed: tenant: { column: 'user_id', claim: 'user_id', mode: 'enforce' }

  // Access rules: dok build converts to Authorization Policy automatically
  access: {
    read:  { roles: ['premium', 'admin'] },  // SELECT
    write: { roles: ['admin'] },             // INSERT, UPDATE
    delete: { deny: true },                  // DELETE blocked
  },
});

// Public data
export const blog = table('blog', {
  id:    col('id',    t.uuid().primaryKey()),
  title: col('title', t.text()),
}, {
  access: {
    read:  { public: true },   // Anyone can read
    write: { roles: ['admin'] },
  },
});
```

#### `t.xxx()` type builders

```typescript
t.text()      // TEXT
t.integer()   // INTEGER
t.real()      // REAL
t.boolean()   // INTEGER (0/1)
t.uuid()      // TEXT — use with primaryKey().default('random')
t.timestamp() // TEXT — CURRENT_TIMESTAMP via default('now')
t.json()      // TEXT (JSON serialized)
t.enum(['a','b','c']) // CHECK constraint
t.serial()    // Auto-increment PK

// Method chaining
.notNull()
.primaryKey()
.unique()
.default('random' | 'now' | value)
.references('table', 'column')
```

#### Third argument to `table()` (security options)

```typescript
table(name, columns, {
  tenant: 'col_name'                     // simple form
    | { column, claim?, mode?: 'enforce' | 'none' }  // detailed
    | false,                             // explicitly public table

  access: {
    read?:   { public:true | auth:true | roles:[...] | deny:true },
    write?:  { ... },                    // INSERT + UPDATE
    delete?: { ... },
    create?: { ... },                    // CREATE TABLE
    all?:    { ... },                    // fallback for ops not listed above
  },
})
```

### 2.2 Writing controllers (`backend/controllers/`)

Import `router` + `db` from `dokkebi:runtime`.

```typescript
// backend/controllers/posts.controller.ts
import { router, db } from 'dokkebi:runtime';
import { posts } from '../models/index.js';
import { eq, and, gt } from 'dokkebi-dsl';

// GET /api/posts
router.get('/api/posts', async (req) => {
  const { rows } = await db
    .select(posts)
    .where(eq(posts.userId, req.session.userId))
    .orderBy(posts.createdAt, 'desc')
    .limit(20)
    .exec();
  return { ok: true, posts: rows };
});

// POST /api/posts
router.post('/api/posts', async (req) => {
  const body = req.json;
  await db
    .insert(posts, {
      userId: req.session.userId,
      title:  body.title,
      content: body.content,
    })
    .exec();
  return { ok: true };
});
```

#### `router` API

```typescript
router.get(path, handler)
router.post(path, handler)
router.put(path, handler)
router.patch(path, handler)
router.delete(path, handler)
```

`handler(req)` receives:

```typescript
req: {
  url: string,
  method: string,
  json: any,           // POST/PUT body (JSON auto-parsed)
  query: object,       // ?a=1&b=2
  params: object,      // :id from /api/users/:id
  headers: object,
  session: object,     // session claims (tenant ID, etc.)
}
```

Returning an object from handler becomes JSON response automatically.

#### `db` DSL

```typescript
// SELECT
const { rows } = await db
  .select(table)                                    // all columns
  .select(table, ['id', 'name'])                    // specific columns only
  .where(eq(table.col, value))                      // single condition
  .where(and(eq(...), gt(...)))                     // compound
  .orderBy(table.col, 'asc' | 'desc')
  .limit(N)
  .offset(N)
  .exec();

// INSERT
await db.insert(table, { col1: v1, col2: v2 }).exec();

// UPDATE
await db
  .update(table, { col: newValue })
  .where(eq(table.id, id))
  .exec();

// DELETE
await db
  .delete(table)
  .where(eq(table.id, id))
  .exec();

// Expressions (for where clause)
eq(col, v), neq(col, v), gt(col, v), gte, lt, lte
like(col, pattern), isNull(col), isNotNull(col)
inList(col, [v1, v2])
and(...exprs), or(...exprs), not(expr)
```

### 2.3 When controllers need explicit permissions (JSDoc annotations)

Use when you cannot put `access` on the DSL model (third-party models, etc.) or want **controller-level** permission declaration. **`dok build` statically extracts** and converts to Authorization Policy.

```typescript
/**
 * Paid content route.
 *
 * @dokkebi-policy table:premium_contents access:read  roles:['premium','admin']
 * @dokkebi-policy table:premium_contents access:write roles:['admin']
 * @dokkebi-policy table:public_blog      access:read  public:true
 * @dokkebi-tenant table:notes column:user_id
 */
router.get('/api/premium/contents', async (req) => {
  // ...
});
```

#### Annotation syntax

```
@dokkebi-policy  table:NAME  access:VERB  [SPEC]

VERB:  read | write | delete | create | all
SPEC:  public:true | auth:true | roles:['r1','r2'] | deny:true

@dokkebi-tenant  table:NAME  column:COL  [claim:CLAIM]  [mode:enforce|none]
```

#### Priority (low → high)

1. Convention inference (table name/column heuristics)
2. DSL `table(...)` options (model definition)
3. **JSDoc `@dokkebi-policy` / `@dokkebi-tenant`** (controller explicit)
4. **`dokkebi.config.js`** `policy` / `authorization` explicit values (highest)

## 3. Security configuration (most important)

### 3.1 Core settings in `dokkebi.config.js`

```js
// dokkebi.config.js
export default {
  proxyMode: 'serverless',        // 'serverless' | 'server'

  database: {
    type: 'd1',                   // 'd1' | 'supabase' | 'appwrite'
    accountId: process.env.D1_ACCOUNT_ID,
    databaseId: process.env.D1_DATABASE_ID,
    apiToken:   process.env.D1_API_TOKEN,
  },

  backend:  { entry: './backend/controllers/index.ts' },
  frontend: { outDir: './dist' },

  // ═══════════════════════════════════════════════════════════
  // Security — most important section
  // ═══════════════════════════════════════════════════════════
  security: {
    // One-line security preset. Choose 'basic' | 'standard' | 'strict'.
    //   'basic'    — no extra enforcement. Legacy-compatible mode.
    //   'standard' — Tenant Policy verify, Authorization warn, auto inference.
    //                → recommended for general apps (recommended default)
    //   'strict'   — Tenant Policy inject, Authorization strict,
    //                queryRegistry strict. → paid/finance/admin apps.
    level: 'strict',

    strictCsp: false,
    activeDefense: { enabled: true, mode: 'enforce' },
  },

  // Below can be set automatically by security.level but manual override works.
  // Explicit values always beat preset.

  // queryRegistry: { strict: true },        // only registered SQL shapes run
  // policy: {
  //   enabled: true,
  //   mode: 'inject',                        // 'verify' | 'inject' | 'off'
  //   tables: {
  //     posts: { tenantColumn: 'user_id', sessionClaim: 'user_id' },
  //   },
  // },
  // authorization: {
  //   enabled: true,
  //   mode: 'strict',                        // 'warn' | 'strict'
  //   jwtSecretEnv: 'JWT_SECRET',
  //   claim: 'role',
  //   rules: {
  //     'SELECT:premium_contents': { roles: ['premium', 'admin'] },
  //     '*': { auth: true },                 // default
  //   },
  // },

  deploy: {
    cloudflarePages: { domain: 'app.example.com' },
  },
};
```

### 3.2 Choosing security level

| App type | Recommended level | Notes |
|---|---|---|
| Personal tools / demos | `'basic'` or `'standard'` | Low security exposure |
| General SaaS / multi-user | `'standard'` | Recommended default |
| **Paid / membership** | **`'strict'`** | **Must use strict** |
| Finance / healthcare / admin | `'strict'` | Must use strict |
| Admin-only pages | `'strict'` | Must use strict |

### 3.3 Server-side validation flow (automatic)

After `dok build` → deploy, every DB request **must pass** these gates (server-side, client cannot bypass):

```
Client (browser WASM)
        │ encrypted SQL
        ▼
[Cloudflare Pages Functions / dok serve]
  ① Envelope size cap        (Phase 1)
  ② Per-session token bucket (Phase 2)
  ③ Nonce duplicate check
  ④ Timestamp validation
  ⑤ HMAC signature verification
  ⑥ AES-256-GCM decrypt
  ⑦ SQL Allowlist             ← always ON
  ⑧ Query Registry strict    ← ON when level: 'strict'
  ⑨ Tenant Policy inject     ← ON when level: 'strict'
  ⑩ Authorization Policy     ← ON when level: 'strict'
  ⑪ ADL Blacklist/Risk
        │ all checks pass
        ▼
     D1 / Supabase / Appwrite execute
```

## 4. Common task patterns

### 4.1 Adding a new route

1. **Check model** — is the table in `backend/models/index.ts`?
   If not, define with `table()`. For security-critical tables, add `access` option.
2. **Write controller** — add `router.METHOD()` in `backend/controllers/`.
3. **Declare permissions** (if needed) — add `@dokkebi-policy` JSDoc on controller.
4. Run `dok dev` or `dok build`.

### 4.2 Adding a new table (migration)

```typescript
// Add definition in backend/models/index.ts
export const articles = table('articles', { ... });
```

```sql
-- backend/db/migrations/004_articles.sql
CREATE TABLE IF NOT EXISTS articles (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  ...
);
```

Applied automatically on `dok build` if D1 credentials exist. Manual apply:

```bash
dok build --skip-migration   # build only
# or wrangler d1 execute dokkebi-db --file=...
```

### 4.3 Using environment variables

```typescript
// backend/controllers/foo.controller.ts
const apiKey = process.env.STRIPE_SECRET_KEY;  // substituted at build time
```

Variables whose names include `SECRET / KEY / TOKEN / PASSWORD / PRIVATE / CREDENTIAL` get
**automatic Opaque Handle protection** (no plaintext in bundle, delivered encrypted via handshake).

### 4.4 Authentication (login/session)

Dokkebi does **not issue sessions for you** — you must implement JWT issuance yourself.
For Dokkebi to recognize session claims:

```typescript
// Login handler (example)
router.post('/api/auth/login', async (req) => {
  const user = await verifyPassword(req.json);
  const token = signJwt({
    user_id: user.id,         // ← Tenant Policy uses this claim
    role: user.role,          // ← Authorization Policy uses this claim
    exp: Math.floor(Date.now()/1000) + 86400,
  });
  return { ok: true, token };
});
```

Manage JWT signing secret via `JWT_SECRET` env var. Change name via
`authorization.jwtSecretEnv` in `dokkebi.config.js`.

## 6. What AI must never do (Anti-patterns)

### ❌ Rely on client-side permission checks

```typescript
// Wrong — bypassable via memory hacking
if (user.plan !== 'premium') {
  throw new Error('Premium members only');
}
```

```typescript
// Correct — enforced on server. Declare via model/JSDoc.
// (DSL access option or @dokkebi-policy)
```

### ✅ Use Signed Unlock Token for paid/high-cost features

Browser WASM branches can be patched, so AI generation, paid features, admin export, etc. should require short-lived server-issued capabilities.

Prefer automatic route guard in `dokkebi.config.js`:

```js
security: {
  capabilities: {
    enabled: true,
    features: {
      'image.generate': {
        roles: ['premium', 'admin'],
        ttlMs: 10000,
        routes: ['POST /api/ai/image'],
      },
    },
  },
}
```

Or declare via controller JSDoc:

```typescript
/**
 * @dokkebi-capability feature:image.generate route:"POST /api/ai/image" roles:['premium','admin'] ttl:10000
 */
router.post('/api/ai/image', async (ctx) => {
  // ctx.capability available after auto guard passes
});
```

Add manual API when more state binding is needed:

```typescript
import { capability } from 'dokkebi:runtime';

const unlock = await capability.unlock('image.generate', {
  state: { projectId, promptHash },
  jwt: authToken,
});
if (!unlock.ok) throw new Error(unlock.error);

// Bind token/proof into execution params or server request material, not simple true/false
```

Declare in `dokkebi.config.js` `security.capabilities`. `DOKKEBI_CAPABILITY_SECRET`
is Worker-only; set 32+ char random in `.env` or Cloudflare Pages Secret.
This defends permission-flag patching; final DB defense is still Authorization Policy / Tenant Policy.

For prerequisite steps, use capability chain with `requires.prev`:

```js
features: {
  'auth.verified':  { public: true,  ttlMs: 60000 },
  'image.generate': { roles: ['premium','admin'], requires: { prev: ['auth.verified'] } },
}
```

```ts
const a = await capability.unlock('auth.verified');
const b = await capability.unlock('image.generate', {
  prev: [{ feature: 'auth.verified', token: a.capability.token }],
});
```

### ✅ Use Bundle Attestation for highly tamperable bundles

Enable `security.attestation.enabled = true` and add `requires: { attest: true }` to protected capabilities. Worker sends random chunk indices as challenge each session; client responds with SHA-256 from in-memory encrypted bundle bytes. Tampered bundles fail manifest check. No user code change—client SDK auto-attests and retries on `CAPABILITY_ATTEST_REQUIRED`.

```js
security: {
  attestation: { enabled: true, sampleSize: 4, ttlMs: 5 * 60_000 },
  capabilities: {
    enabled: true,
    features: {
      'image.generate': { roles: ['premium','admin'], requires: { attest: true } },
    },
  },
}
```

### ✅ Operations admin: password + IP restriction together

For projects exposing `/_dokkebi/_panel`, set long `DOKKEBI_ADMIN_PASSWORD` in `.env` or Cloudflare Pages Secret. For IP restriction, set `security.panelIpGuard: true` in `dokkebi.config.js` and limit via `DOKKEBI_PANEL_ALLOWED_IPS`.

```js
security: {
  panelIpGuard: true,
}
```

```env
DOKKEBI_ADMIN_PASSWORD=your_secure_password
DOKKEBI_PANEL_ALLOWED_IPS=203.0.113.10,198.51.100.0/24
```

Default `security.panelIpGuard` is `false`; when off, env value is ignored. When on without `DOKKEBI_PANEL_ALLOWED_IPS`, `dok build` warns. Do not edit template `_panel` code—control via config/env.

### ❌ Edit `worker/api/_dokkebi/*` directly

These files are auto-generated by `dok build`. Edits are overwritten on next build.
Change policy via `dokkebi.config.js` or model/controller annotations.

### ❌ Expose `process.env.SECRET_*` in plaintext

Dokkebi auto-handles Opaque Handle. But **never use in client code (`frontend/`)**.
`frontend/` is normal browser env—use only `import.meta.env.VITE_*`.

### ❌ Write directly to `dist/` or `functions/`

Auto-generated directories. Always regenerate with `dok build`.

### ❌ Omit tenant column

In multi-user apps, missing tenant columns like `posts.userId` breaks isolation.
`policyInference` prints warnings—always check build logs.

### ❌ Assemble SQL manually (string concatenation)

```typescript
// Wrong — Allowlist reject + SQL injection
await db.exec(`SELECT * FROM posts WHERE id = '${userInput}'`);
```

```typescript
// Correct — use DSL
await db.select(posts).where(eq(posts.id, userInput)).exec();
```

## 7. Debugging / troubleshooting

### "Could not infer tenant column" warning

```bash
[tenant] Could not infer tenant column for table 'X'.
```

Fix:
1. Add standard column like `user_id` / `owner_id` to model, or
2. Explicit `table('X', {...}, { tenant: 'col_name' })`, or
3. For public tables `table('X', {...}, { tenant: false })`

### "queryId not in registry" error

With `security.level: 'strict'` + `queryRegistry.strict: true`,
unregistered SQL shape was called at runtime.

Fix:
1. Re-run `dok build` (collects all SQL at build time).
2. For dynamic SQL, register with `// @dokkebi-query: SELECT ... FROM ...` comment.
3. Temporary: `queryRegistry: { strict: false }`.

### "AUTH_REQUIRED" / "ROLE_FORBIDDEN" (403)

Server Authorization Policy rejected the request.

Fix:
1. Is client sending `Authorization: Bearer <jwt>`?
2. Does JWT `role` claim match policy rules?
3. Check `authorization.rules` in `dokkebi.config.js` or model/JSDoc annotations.

### "TENANT_MISSING" (403)

Session lacks tenant claim, or SQL missing column condition required by policy.

Fix:
1. Does login JWT include correct claims (`user_id`, etc.)?
2. Did client call `ctx.setSessionTenant({ user_id: '...' })`?
3. Can you use `mode: 'inject'` for auto-injection?

## 9. Core security principles summary

> 1. **Do not trust the client.** WASM/memory hacking is always possible.
> 2. **Server middleware is source of truth.** All permission/tenant validation on server.
> 3. **Prefer declarative security (DSL access / JSDoc).** Policy stays with code.
> 4. **Use `security.level: 'strict'` actively.** One line enables all defenses.
> 5. **Always check build logs.** Inference results and warnings are printed.

## 10. SEO — automatic SEO pipeline

Dokkebi is CSR + WASM backend so SSR is impossible, but **build-time prerender + runtime Edge SEO Renderer** provide page-specific meta to search engines/social crawlers. No extra user code—all via `dokkebi.config.js` + router/model auto-scan.

### 10.1 Flow

```
Build time (dok build)
  ① Route scan (frontend/src/**) — infer title/description
  ② Static routes → dist/<path>/index.html prerender (meta + JSON-LD inject)
  ③ Dynamic routes → seo.dynamic SQL or D1 enumerate → static HTML expansion
  ④ Generate sitemap.xml + robots.txt
  ⑤ Emit functions/_dokkebi-seo/[[path]].js (Edge Renderer) + functions/_middleware.js (bot branch)

Runtime (Cloudflare Pages)
  Bot UA request ── _middleware.js checks UA
                │ if bot
                ▼
              forward to /_dokkebi-seo/<path>
                │
                ▼
              KV cache (SEO_CACHE) hit → immediate response
                │ on miss
                ▼
              D1 lookup (single row) → inject meta into base HTML → KV 24h store
              Normal UA gets SPA index.html static response
```

Debug via response header `x-dokkebi-seo: HIT|MISS|PASS|NO-DB|DB-ERR|NOT-FOUND`.

### 10.2 `seo` block in `dokkebi.config.js`

```js
seo: {
  baseUrl: 'https://example.com',         // sitemap absolute URL base
  defaults: {
    siteName: 'My App',
    locale: 'ko',
    description: 'Default site description (fallback when description inference fails)',
    image: '/og-default.png',             // og:image fallback
    twitterCard: 'summary_large_image',
  },

  // Static routes — explicit title/description. Supplement when router scan misses.
  routes: {
    '/':              { title: 'Home', description: '...', image: '/og/home.png' },
    '/about':         { title: 'About', description: '...' },
    '/pricing':       { title: 'Pricing', description: '...' },
  },

  // Dynamic routes — expand to static HTML at build via SQL on D1.
  // Runtime Edge SEO Renderer uses same SQL for single-row lookup.
  dynamic: [
    {
      path: '/:lang/:username/post/:slug',  // router pattern
      query: `
        SELECT
          p.locale     AS lang,
          u.username   AS username,
          p.slug       AS slug,
          p.title      AS title,
          p.excerpt    AS description,
          p.updated_at AS updated_at
        FROM posts p
        JOIN users u ON u.id = p.user_id
        WHERE p.published = 1
          AND u.username IS NOT NULL
          AND p.slug IS NOT NULL
      `,
      // Column mapping auto when SELECT alias matches route :param name.
      // Explicit:
      // columns: { titleCol: 'title', descCol: 'description', imageCol: null, timeCol: 'updated_at' },
    },
  ],

  // edgeRenderer auto-enabled when dynamic has 1+ entry. To disable:
  // edgeRenderer: { enabled: false },
  // edgeRenderer: { enabled: true, cacheTtlSeconds: 86400 }, // KV cache TTL
},
```

### 10.3 Static prerender — route meta extraction priority

```
1) Page component top JSDoc  /** @dokkebi-seo title: ... description: ... image: ... */
2) seo.routes['/path']         (config explicit — recommended)
3) <Helmet> / next/head etc. library patterns
4) Component export default function name → natural language inference (low confidence)
```

Check `dist/.dokkebi/seo-report.md` after build for extraction/confidence. Specify low-confidence routes in `seo.routes`.

### 10.4 Dynamic routes — `seo.dynamic` rules

- **`path`**: Router pattern. `:param` format. Multiple `:` allowed.
- **`query`**: SELECT SQL. Result column aliases auto-map when they match route `:param` names.
  - Required: at least alias for last `:` segment (example: `slug`).
  - Recommended: `title`, `description`, `updated_at` (for lastmod), optional `image`.
- Build-time enumerate needs D1 credentials (`.env: D1_API_TOKEN`).
- Without credentials or when `database.type !== 'd1'`, SEO dynamic routes are skipped.

### 10.5 Cloudflare Pages bindings

Recommended bindings in `wrangler.toml`:

```toml
[[d1_databases]]
binding = "DB"                    # Required. Edge Renderer uses for D1 lookup.
database_name = "..."
database_id = "..."

[[kv_namespaces]]
binding = "SEO_CACHE"             # Optional. 24h cache. Without it, every request hits D1 (performance only).
id = "..."                        # Create via `wrangler kv:namespace create SEO_CACHE`.
```

Works without KV binding. `x-dokkebi-seo: MISS` every call is normal if no KV.

### 10.6 Security — Tenant Policy vs SEO

Edge SEO Renderer serves bots with **no login session**. With Tenant Policy `strict` / `enforce`, requests get `TENANT_MISSING`.

**Fix**: public SEO tables use `optional` mode.

```js
policy: {
  enabled: true,
  mode: 'verify',
  tables: {
    posts:       { tenantColumn: 'user_id', mode: 'optional' },  // isolate when logged in, bots pass
    users:       { mode: 'optional' },
    blog_profiles: { mode: 'optional' },
  },
}
```

`mode: 'optional'` — inject isolation SQL when JWT claim present, otherwise pass through.

### 10.7 Bot UA detection scope

Auto-routed bots (extensible):
`googlebot, bingbot, slurp, duckduckbot, yandexbot, baiduspider, sogou, applebot, naver/yeti, daum/kakao, twitterbot, facebookexternalhit, linkedinbot, slackbot, discordbot, telegrambot, whatsapp, gptbot, chatgpt-user, claudebot, perplexitybot, amazonbot, bytespider, *bot, *spider, *crawler`, etc.

Normal users (browsers) get SPA response → CSR proceeds normally.

### 10.8 Debugging bot responses

```bash
# Verify — x-dokkebi-seo: MISS header + page-specific meta
curl -I -A "Googlebot/2.1" https://example.com/posts/hello-world

# Function diagnostics — call /_dokkebi-seo/<path> directly
curl -i https://example.com/_dokkebi-seo/posts/hello-world
# No x-dokkebi-seo header means routing failed → check functions/_dokkebi-seo/[[path]].js exists.

# If second call stays MISS not HIT, no KV (SEO_CACHE) binding.
```

Status header meanings:
| Header value | Meaning |
|---|---|
| `HIT` | KV cache hit (24h) |
| `MISS` | D1 lookup success, cached |
| `PASS` | No route match, SPA response as-is |
| `NO-DB` | No `env.DB` binding |
| `DB-ERR` | SQL failed (Tenant Policy block, etc.) |
| `NOT-FOUND` | Matched but no D1 row |

### 10.9 Anti-patterns

❌ **Edit `functions/_dokkebi-seo/[[path]].js` directly** — auto-generated, overwritten each build. Change via `seo.dynamic` config or route meta.

❌ **Tenant strict + public pages** — bot responses always blocked. Use `optional` mode.

❌ **SELECT sensitive columns in `seo.dynamic.query`** — exposed in Edge Renderer HTML. Only public-safe columns.

❌ **Too many `:param`** — dynamic routes over 4 segments can bloat sitemap / indexing rejection. Prefer category pages.

## 12. D1 sharding & read scale (Phase A + B merged)

> **Area AI gets wrong most often.** Follow this section exactly for safety;
> improvising almost certainly breaks data isolation and transaction integrity.

### 12.1 Decision — what to enable

| Situation | Choice |
|---|---|
| ~thousands concurrent, read-heavy | **Single D1 as-is** (enable nothing) |
| ~10k concurrent, global users | Add one line: `database.sessions: true` |
| tens of thousands+, write limit hit | `database.type: 'd1-sharded'` + `shards[]` + `strategy` |
| Single hot key concentration (live room, viral post) | **Not sharding — use Durable Object** |

### 12.2 Step 1 — Read replica (1 line, 30 seconds)

```js
// dokkebi.config.js
database: {
  type: 'd1',
  // ... existing config unchanged
  sessions: true,            // ← add this one line only
},
```

- All `SELECT` auto-route to nearest D1 replica (lower latency, higher concurrency).
- Response attaches `Set-Cookie: __d1b=...; HttpOnly; SameSite=Lax` → same user's
  "write then read" consistency guaranteed automatically.
- **No controller code changes.** AI must never add `withSession()` manually.
  Dokkebi injects at build time.

### 12.3 Step 2 — Choose shard key (most important step)

Shard key must be **the column where one transaction finishes in one shard**.
Do not shard unless all four are ✓:

- [ ] Most queries are `WHERE {key} = ?`?
- [ ] One transaction only operates within same key value? (no cross-key transactions)
- [ ] Same column as `policy.tables[*].sessionClaim` in policy engine? (auto-verified at build)
- [ ] Traffic not 80%+ concentrated on one key? (if concentrated, no sharding — use Durable Object)

### 12.4 Step 3 — Config + provisioning

Default `dokkebi.config.js` already has commented `// type: 'd1-sharded'` block.
Uncomment and fill, then:

```bash
dok db:provision   # Auto-create all shard D1s + update wrangler.toml [[d1_databases]]
dok migrate        # Fan-out schema to all shards + global
```

`dok db:provision` is idempotent — reuses existing D1 by name, skips filled entries.
Safe to run multiple times.

### 12.5 Step 4 — Controller patterns (follow exactly)

**Correct pattern**:

```typescript
import type { Context } from 'dokkebi:runtime';

// READ — same user_id always same shard
export const listOrders = async (ctx: Context) => {
  const { user_id } = ctx.session;
  const db = ctx.shardFor({ user_id });               // ✅ deterministic routing
  return db.query('SELECT * FROM orders WHERE user_id = ?', [user_id]);
};

// WRITE — same handle for writes. primary auto-selected.
export const placeOrder = async (ctx: Context) => {
  const { user_id } = ctx.session;
  const { product_id, qty, total } = await ctx.body();
  const db = ctx.shardFor({ user_id });
  await db.exec(
    'INSERT INTO orders(user_id, product_id, qty, total_price) VALUES (?,?,?,?)',
    [user_id, product_id, qty, total],
  );
  return { ok: true };
};

// FAN-OUT — ops/aggregation only. User code responsible for merging results.
export const adminTotal = async (ctx: Context) => {
  const rows = await ctx.fanout((db) => db.query('SELECT COUNT(*) AS n FROM orders'));
  return { total: rows.reduce((s, r) => s + (r[0]?.n ?? 0), 0) };
};

// GLOBAL — shared lookup tables (products, coupons, …)
export const getProduct = async (ctx: Context) => {
  const g = ctx.global();
  return g.query('SELECT * FROM products WHERE id = ?', [Number(ctx.params.id)]);
};
```

### 12.6 Never do (AI anti-patterns)

- ❌ **Never read another user's data on one handle**
  ```typescript
  const db = ctx.shardFor({ user_id: A });
  db.query('SELECT * FROM orders WHERE user_id = ?', [B]);   // blocked by policy engine
  ```
- ❌ **No implicit cross-shard**: no manual `for (const s of shards) { ... }`.
  Always use explicit `ctx.fanout()`.
- ❌ **No cross-shard transactions**: D1 has no cross-DB transactions. Multi-key work needs saga pattern.
- ❌ **No `ctx.db.withSession()` / direct `env.DB`**: auto-injected at build.
  AI adding it causes double injection and broken cookies.
- ❌ **Do not freely change shard count**: same key could land on different shard. Changes only via Phase C
  (`dok db:reshard`) workflow.

### 12.7 Dynamic SQL routing hints

Dokkebi cannot tell read vs write when prefix is not `SELECT` for dynamically composed SQL.
Add one-line hint at start:

```typescript
const sql = '/*!read*/ '  + buildSelectSql(filters);  // prefer replica
const ups = '/*!write*/ ' + buildUpsertSql(...);      // force primary
```

### 12.8 Auto validation at build/deploy

| Check | When | Result |
|---|---|---|
| Missing `strategy.key` | `dok build` | Error (build blocked) |
| `strategy.key` ≠ `policy.tables[*].sessionClaim` | `dok build` | Warning (error if `policy.strict:true`) |
| Sharding mode but `sessions: false` | `dok build` | Warning |
| Missing shard binding in `wrangler.toml` | `dok deploy` preflight | Error (deploy blocked) |
| Warnings accumulated with `--preflight strict` | `dok deploy` | All become errors |

### 12.9 Single → sharding migration checklist

1. Change `database.type` to `'d1-sharded'`, write `shards`/`strategy`.
2. `dok db:provision` → fill `databaseId` from output into `.env` or config.
3. `dok migrate` → apply schema to all shards + global.
4. Convert controllers to `ctx.shardFor({ [strategy.key]: value })` in bulk.
5. Re-verify policy engine `sessionClaim` matches `strategy.key`.
6. (Phase C) Existing data distribution via `dok db:reshard backfill` (not implemented — manual SQL fanout needed).

> Design details: `dokkebi-cli/docs/design/SHARDING.md`, user guide:
> dokkebi-site `/#/sharding` page.
