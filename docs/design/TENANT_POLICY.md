- **Version**: 1.0 (implemented — Stage 1 & 2)
- **Status**: v5.1 (verify) + v5.2 (inject) release
- **Scope**: Stage 1 (policy metadata + verify mode) + Stage 2 (auto-inject mode)

## 0. Implementation Summary (v5.1 + v5.2)

```
dokkebi.config.js → normalizePolicyConfig() → allowlist v2 schema
                                           ↓
                     worker/api/_dokkebi/db.ts  (v6 template)
                       ├─ _policyMeta (build-time embed)
                       ├─ verifyTenantPolicy()   (Stage 1)
                       ├─ injectTenantPolicy()   (Stage 2)
                       └─ _setTenant branch        (session claim update)

Client flow:
  login success → ctx.setSessionTenant({user_id, ...}) → encrypted channel →
    Pages Function updates _dokkebi_sessions.tenant_json
  all subsequent db requests: parse tenant_json on session lookup → verify/inject
```

### Usage Examples

**1) Single-user app** (default, no config needed):
```js
// dokkebi.config.js
export default {
  // omit policy section → policy engine disabled, legacy v4 behavior
};
```

**2) Multi-tenant SaaS — verify mode** (blocks developer mistakes):
```js
export default {
  policy: {
    enabled: true,
    mode: 'verify',              // 'verify' | 'inject' | 'off'
    sessionClaim: 'user_id',
    strict: true,
    tables: {
      orders:   { tenantColumn: 'user_id',  mode: 'enforce' },
      posts:    { tenantColumn: 'author_id', mode: 'enforce' },
      products: { mode: 'none' },     // public table
    }
  }
};
```

**3) Auto-inject mode** (server fills in even if the developer forgets):
```js
export default {
  policy: {
    enabled: true,
    mode: 'inject',              // auto-inject on verify failure
    sessionClaim: 'user_id',
    tables: { orders: { tenantColumn: 'user_id', mode: 'enforce' } }
  }
};
```

### Session Tenant Setup (after login)

Call from the backend controller after successful login verification:
```typescript
// backend/controllers/auth.ts
export async function login(ctx, email, password) {
  const user = await db.query(users).where(u => u.email.eq(email)).first();
  if (!user || !verifyPassword(password, user.password_hash)) throw new Error('INVALID');

  // Bind tenant claims to the current session — applied automatically on all subsequent db requests
  await ctx.setSessionTenant({ user_id: user.id });

  return { id: user.id, email: user.email };
}
```

Internal behavior: `ctx.setSessionTenant(obj)` sends `{_setTenant: obj}` to `POST /api/_dokkebi/db` → server runs `UPDATE _dokkebi_sessions SET tenant_json = ? WHERE session_id = ?`. `obj === null` clears on logout.

### Per-table `sessionClaim` (v5.4+) — tenant isolation with hash IDs only, no JWT

Tenant Policy is **independent of login / JWT**. Session `tenant_json` is free-form JSON, so **any value** used for user identification (hash token, device ID, anonymous cookie, etc.) can serve as the tenant.

Typical example — projects like **notofly** that use different hash tokens per table:

```js
// dokkebi.config.js (autogen — generated by dok policy:scaffold)
policy: {
  enabled: true,
  mode: 'verify',
  sessionClaim: 'creator_token',   // global default (fallback)
  tables: {
    notos:              { tenantColumn: 'creator_token',      sessionClaim: 'creator_token' },
    messages:           { tenantColumn: 'sender_token',       sessionClaim: 'sender_token' },
    users:              { tenantColumn: 'id',                 sessionClaim: 'user_id' },
    noto_collaborators: { tenantColumn: 'collaborator_token', sessionClaim: 'collaborator_token' },
    push_subscriptions: { tenantColumn: 'token',              sessionClaim: 'token' },
    message_replies:    { tenantColumn: 'author_token',       sessionClaim: 'author_token' },
  },
}
```

Frontend — bind **multiple kinds of hash IDs** to the session in one `setSessionTenant` call:

```typescript
// App init (e.g. React useEffect, no login/signup required)
await ctx.setSessionTenant({
  creator_token:      localStorage.getItem('creator_token')      || undefined,
  sender_token:       localStorage.getItem('sender_token')       || undefined,
  collaborator_token: localStorage.getItem('collaborator_token') || undefined,
  user_id:            authState?.userId                           || undefined,
});
```

Engine claim resolution order (evaluated per table):

1. `tables[X].sessionClaim` — session key explicitly set on the table (clearest)
2. `policy.sessionClaim` — global default (backward compatible)
3. `tenantColumn` name as-is — conventional fallback (column name = session key)

For example, `SELECT * FROM notos WHERE creator_token = ?` uses `notos.sessionClaim = 'creator_token'` and compares against the session's `creator_token` value. For convention cases where **column name and session key differ** (like `users.id`), only specify `sessionClaim: 'user_id'`. Everything else is auto-placed by `dok policy:scaffold` using the column name as the session key.

> **Key point**: It does not have to be a "logged-in user" — any identifiable value works. Anonymous users, hash IDs, and device tokens are all OK.

### Policy Violation Response

```json
{
  "ok": false,
  "error": "WHERE clause is missing orders.user_id = ? condition.",
  "code": "NO_TENANT_FILTER",
  "table": "orders"
}
```

HTTP 403 + `tenant_policy_violation` event recorded in `_dokkebi_security`.

### Error Code Table

| code | meaning | handling |
|---|---|---|
| `TENANT_MISSING` | session missing the claim | call `ctx.setSessionTenant()` |
| `NO_WHERE` | WHERE clause missing | add WHERE (or use `mode: 'inject'`) |
| `NO_TENANT_FILTER` | tenant column condition missing | add `WHERE user_id = ?` |
| `TENANT_MISMATCH` | sent value does not match session | treat as attack attempt (403) |
| `LOOSE_OR` | top-level OR in WHERE | rewrite as AND chain |
| `INSERT_NO_COLUMNS` | INSERT without column list | use `INSERT INTO t (c1, c2) VALUES (...)` |
| `INSERT_MISSING_TENANT_COL` | INSERT columns missing tenant | add `tenant_col` |
| `UNSUPPORTED_INSERT_SUBQUERY` | INSERT ... SELECT not supported | split query or use `optional` mode |
| `INJECT_FAILED` | parsing failed during inject | simplify SQL structure |

### Known Limitations (v1.0)

- **INSERT … SELECT** subqueries are rejected in strict mode (parser simplicity). Relax with `mode: 'optional'` if needed.
- **CTE (WITH)** — verify only works on the final operation; full recursive checks on inner SELECTs are not supported.
- **INSERT single VALUES tuple** only for inject. Multiple tuples: verify only.
- **Dynamic table names** (variable substitution) cause parse failure → rejected when `strict=true`.
- **Admin bypass**: only when `tenantContext._isAdmin === true`. **⚠ Security (C-2 fix):** clients can no longer set `_isAdmin` (or any `_`-prefixed key) via `ctx.setSessionTenant()` — the proxy rejects reserved keys (`TENANT_RESERVED_KEY`). Admin elevation must come from a server-trusted path (worker-side `_login` role claims + Authorization Policy), never from client-supplied tenant values.

## 0.0 Stage Dependencies · Default Policy (Framework Philosophy)

Dokkebi is a framework that supports **diverse use cases** from single-user apps to multi-tenant SaaS. Each stage is designed to be **independently opt-in / opt-out**, with defaults per the table below.

| stage | protects | default | activation | dependency |
| ----- | -------- | ------- | ---------- | ---------- |
| **Allowlist** | table/operation-level SQL permission | **ON (since v4)** | always active (defense in depth) | none |
| **Stage 3 (Query Registry)** | SQL shape-level permission | **ON (v5 default)** | opt-out via `queryRegistry.enabled: false` | none (independent) |
| **Stage 1 (Tenant Verify)** | missing tenant column detection | **OFF** | `policy.enabled: true, policy.mode: 'enforce-verify'` | Stage 3 recommended (not required) |
| **Stage 2 (Tenant Inject)** | auto-inject tenant conditions | **OFF** | `policy.mode: 'enforce-inject'` | requires Stage 1 |

### Recommended Implementation and Release Order

```
v5.0 — Stage 3 (Query Registry) standalone release  [~1.5–2 weeks]
  └─ all apps benefit automatically (single-user apps also get fixed SQL shapes)

v5.1 — Stage 1 (Tenant Verify) opt-in added   [+1 week]
  └─ multi-tenant apps roll out gradually (warn only, no block)

v5.2 — Stage 2 (Tenant Inject) opt-in added   [+1 week]
  └─ multi-tenant apps get auto-injected tenant conditions
```

### Activation Examples by Use Case

**Single-owner app (e.g. personal blog, single shop):**
```js
// dokkebi.config.js (same as defaults, no config needed)
export default {
  // Stage 3 auto ON
  // Stage 1, 2 OFF
};
```

**Multi-tenant SaaS (e.g. marketplace with multiple sellers):**
```js
export default {
  queryRegistry: { enabled: true, raw: 'deny' },
  policy: {
    enabled: true,
    mode: 'enforce-inject',        // auto-inject
    sessionClaim: 'user_id',
    tables: {
      orders:   { tenantColumn: 'user_id' },
      products: { tenantColumn: 'seller_id' }
    }
  }
};
```

> **Core idea**: The framework provides capability; developers choose per use case. Defaults are "safe and light for the majority."

## 0. TL;DR

D1 does not provide RLS (Row-Level Security). But Dokkebi **forces all SQL through a single gate** — the Cloudflare Pages Function — so an extra policy layer on that gate can **structurally enforce tenant isolation** (e.g. row-level isolation by `user_id`) even when the application is written incorrectly.

This document extends the existing SQL Allowlist (`sql-allowlist.json` v1) to:
- add per-table tenant policy metadata to the **v2 schema**, and
- inject a **runtime policy engine** into the Pages Function (`worker/api/_dokkebi/db.ts`), and
- define gradual rollout from **verify mode (Stage 1)** → **auto-inject mode (Stage 2)**.

## 1. Background / Problem Statement

### 1.1 Current State (v1 Allowlist)

```json
{
  "version": 1,
  "tables": [
    { "name": "orders", "ops": ["SELECT", "INSERT", "UPDATE"] }
  ],
  "rawAllowed": false
}
```

- Only checks table/operation-level permission
- After an attacker completes a legitimate handshake, `SELECT * FROM orders` **exposes all users' orders**
- If a developer omits `WHERE user_id = ?` in a controller, the entire app dataset leaks

### 1.2 D1 Constraints

- Cloudflare D1 does not support DB-level policies like PostgreSQL RLS
- Policy must be enforced on "the path all SQL must take" — for Dokkebi, that single path is Pages Function `/api/_dokkebi/db`

### 1.3 Goals

| goal | level |
| ---- | ----- |
| prevent tenant leaks from controller mistakes | Must |
| malicious client cannot read another tenant's data | Must |
| backward compatibility for existing projects (v1 unchanged) | Must |
| intuitive declarative config (natural in models/DSL) | Should |
| minimal runtime overhead (simple SQL: ≤+0.1ms) | Should |
| auto-inject all queries (developer need not care) | Could (Stage 2) |

### 1.4 Non-Goals (Out of Scope)

- block all malicious queries (SQL injection: existing allowlist + DSL parameter binding)
- DB-level encryption, row-level RBAC
- Query Registry (Stage 3, separate document)
- multi-dimensional policy with multiple tenant axes (v1.0: single axis only, e.g. `user_id` / `owner_id`)

---

## 2. Terminology

| term | meaning |
| ---- | ------- |
| **Tenant** | data isolation unit. Usually user (`user_id`) or org (`org_id`). Current design: single axis. |
| **Tenant Column** | column identifying tenant on that table. e.g. `orders.user_id` |
| **Session Claim** | tenant identifier held by client session. e.g. logged-in user's `id` or `sub` |
| **Policy** | tenant requirement for a table. `enforce` / `optional` / `none` |
| **Verify mode (enforce-verify)** | parse WHERE and confirm correct tenant filter; reject if missing |
| **Auto-inject mode (enforce-inject)** | rewrite WHERE to force-add tenant filter on the server |

## 4. Stage 1 — Policy Metadata + Verify Mode

### 4.1 Declaration Styles (three coexist)

Priority: **explicit policy file > model DSL annotation > heuristic inference**

#### (a) `backend/policy.ts` (explicit, recommended)

```typescript
// backend/policy.ts
import type { DokkebiPolicy } from 'dokkebi:runtime';

export const policy: DokkebiPolicy = {
  tenant: {
    source: 'session',          // 'session' | 'jwt-claim'
    claim: 'user_id',           // use session.user_id as default tenant
  },
  tables: {
    users:    { tenantColumn: 'id',       mode: 'enforce' },
    orders:   { tenantColumn: 'user_id',  mode: 'enforce' },
    products: { mode: 'none' },           // public table
    posts:    { tenantColumn: 'author_id', mode: 'optional' }, // partially public
  },
  // default for undeclared tables: 'none' (backward compatible) or 'deny' (strict)
  default: 'none',
};
```

#### (b) Model DSL Annotation (DX-first)

```typescript
// backend/models/order.model.ts
import { table } from 'dokkebi-dsl';

export const orders = table('orders')
  .ownedBy('user_id');     // ← one line declares tenant policy automatically
```

#### (c) Heuristics (last fallback, **disabled by default**)

- if table has `user_id` / `owner_id` / `tenant_id` / `author_id`, auto-register `optional` mode
- risk: false positives → default OFF; enable only via `policy.inferFromColumns: true` in `dokkebi.config.js`

### 4.2 v2 Allowlist Schema

```json
{
  "version": 2,
  "tenant": {
    "source": "session",
    "claim": "user_id"
  },
  "tables": [
    {
      "name": "orders",
      "ops": ["SELECT", "INSERT", "UPDATE"],
      "policy": {
        "mode": "enforce",
        "tenantColumn": "user_id"
      }
    },
    {
      "name": "products",
      "ops": ["SELECT"],
      "policy": { "mode": "none" }
    }
  ],
  "rawAllowed": false,
  "defaultMode": "none",
  "generatedAt": "2026-04-20T00:00:00.000Z"
}
```

Backward compatibility:
- tables without `policy` field → apply `defaultMode` (default `"none"`)
- v1 files load as-is; all tables treated as `"none"` → **existing projects unchanged**

### 4.3 Session Context

Pages Function already stores sessions in D1 (`_dokkebi_sessions`). Add an optional field:

```sql
ALTER TABLE _dokkebi_sessions ADD COLUMN tenant_json TEXT;
-- serialized JSON like {"user_id": "abc-123", "org_id": "acme"}
```

- updated automatically when login controller calls APIs like `ctx.session.set('user_id', user.id)`
- Pages Function parses `tenant_json` on session lookup and includes it in runtime context

### 4.4 Verify Mode Algorithm (enforce-verify)

Input:
- `sql` (parsed and normalized), `params`, `tenantContext = { user_id: 'abc-123' }`

Algorithm:
```
for each table T referenced by sql:
  policy = allowlist.policy(T)
  if policy.mode == 'none':         continue
  if policy.mode == 'optional':     continue
  if policy.mode == 'enforce':
    tenantCol = policy.tenantColumn
    sessionClaim = tenant.claim              # e.g. 'user_id'
    expectedValue = tenantContext[sessionClaim]

    # SELECT/UPDATE/DELETE: require `T.tenantCol = ?` in WHERE
    # INSERT: column value must equal expectedValue

    if not hasTenantPredicate(sql, T, tenantCol, expectedValue):
      reject 403, reason = "tenant policy violation: $T requires $tenantCol = session.$sessionClaim"
```

#### 4.4.1 SELECT / UPDATE / DELETE

Example: `SELECT * FROM orders WHERE user_id = ? AND status = 'paid'`

- WHERE tree must contain `orders.user_id = ?`
- `params[i]` at `?` must match `tenantContext.user_id`
- reject loose OR (e.g. `WHERE user_id = ? OR admin = 1`)
- OK if present anywhere in AND tree

#### 4.4.2 INSERT

Example: `INSERT INTO orders (user_id, total) VALUES (?, ?)`

- column list must include `user_id`, and corresponding `params[0]` must match `tenantContext.user_id`
- reject `INSERT INTO orders VALUES (...)` without column list (avoid column-order dependency)

#### 4.4.3 JOIN

Example: `SELECT o.*, p.name FROM orders o JOIN products p ON p.id = o.product_id WHERE o.user_id = ?`

- apply rules per referenced table
- `products.mode == 'none'` → pass; `orders` requires `user_id` check

#### 4.4.4 Subquery / CTE

- CTE: each SELECT in WITH clause checked independently
- Subquery: recursive check with same rules as top-level WHERE

### 4.5 Parser Choice

- **v1 implementation**: extend existing regex-based `sqlAllowlist.js` + small dedicated tokenizer (Cloudflare Workers bundle size)
- **accuracy limit**: complex subqueries may false-positive → `policy.strict: false` warns; `strict: true` rejects
- **v2 upgrade option**: WASM-compiled lightweight SQL parser (Workers-compatible subset of `node-sql-parser`) — evaluate after v1 stabilizes

### 4.6 Failure Response

```json
{
  "error": "tenant policy violation: orders.user_id does not match session user_id.",
  "code": "TENANT_POLICY_VIOLATION",
  "table": "orders",
  "expectedClaim": "user_id"
}
```

- HTTP 403
- `tenant_violation` event in `_dokkebi_security`

### 4.7 Environment Variables / Modes

| variable | default | meaning |
| -------- | ------- | ------- |
| `DOKKEBI_POLICY_MODE` | `verify` (v2 projects), `off` (v1 projects) | `off` / `verify` / `inject` / `deny-all` |
| `DOKKEBI_POLICY_STRICT` | `true` | reject (`true`) or pass (`false`) on parse failure |

### 4.8 Minimal Change Scope (Stage 1)

- `src/core/sqlAllowlist.js` — v2 schema support, policy extraction in `extractAllowlist()`
- `src/core/policyExtractor.js` (new) — parse `backend/policy.ts` / collect model DSL annotations
- `src/core/projectGenerator.js` — insert tenant verify section in Pages Function template (v4 → v5)
- `src/commands/build.js` — embed v2 allowlist
- `src/commands/serve.js`, `src/commands/dev.js` — same verify logic
- `docs/design/TENANT_POLICY.md` — this document

## 5. Stage 2 — Auto-Inject Mode (enforce-inject)

### 5.1 Concept

Stage 1: "block if developer forgot." Stage 2: "server fills in even if developer forgot."

Pros:
- developers need not write `WHERE user_id = ctx.user.id` every time
- **eliminates** leaks from omission

Cons:
- SQL rewrite → complexity ↑, strongly depends on parser accuracy
- must prevent duplicate inject when tenant condition already present

### 5.2 Injection Rules

| operation | rewrite |
| --------- | ------- |
| SELECT | `SELECT ... FROM T` → `SELECT ... FROM T WHERE T.<tenantCol> = ?` (merge with `AND` if WHERE exists) |
| UPDATE | `UPDATE T SET ... WHERE ...` → `UPDATE T SET ... WHERE (...) AND T.<tenantCol> = ?` |
| DELETE | `DELETE FROM T WHERE ...` → `DELETE FROM T WHERE (...) AND T.<tenantCol> = ?` |
| INSERT | add `<tenantCol>` to column list if missing + append `tenantContext.<claim>` to params |
| JOIN | inject per table, use table aliases |

### 5.3 Parameter Handling

- rewritten SQL has N+k `?` placeholders (k = injected tenant count)
- append `tenantContext[claim]` to **end** of `params`
- D1 uses positional parameters — order matters → parser must track `?` indices in AST

### 5.4 Duplicate Inject Prevention

Do not re-inject if `WHERE T.tenant_col = ?` already exists (when value matches) / reject on mismatch.

### 5.5 Opt-in / Gradual Rollout

- default on project creation: **Stage 1 (verify) mode**
- Stage 2 activation is explicit: `security.policyMode: 'inject'` in `dokkebi.config.js`
- or per table: `{ "mode": "inject" }`

### 5.6 Test Strategy

- unit tests: 100+ SQL samples (SELECT / JOIN / UNION / CTE / subquery / INSERT variants)
- fuzz tests: random SQL generator, compare before/after inject
- property tests: "post-inject SQL = pre-inject SQL + tenant condition" holds logically

## 10. FAQ / Known Limitations

### Q1. Queries with dynamic table names?

- parse failure → reject if `strict=true`. Dynamic tables are not recommended in `dokkebi-dsl` anyway.

### Q2. Aggregate-only queries like `SELECT COUNT(*) FROM orders`?

- `enforce` mode still requires tenant condition → need `WHERE user_id = ?`
- admin UI needing global stats: separate public table or view registered with `mode: "none"`

### Q3. Multiple tenants (e.g. user + org)?

- v1.0: single axis. v2.0 planned: `policy.tenants: [...]` and `policy.tenantColumns: { user_id, org_id }`

### Q4. How do admins bypass?

- admin session marked `tenant_json.isAdmin = true` + Pages Function bypasses policy for admin sessions only
- still **recommended**: separate endpoints for admin APIs (minimize attack surface)

### Q5. What if an attacker manipulates the tenant value?

- tenant values in `params` come **only from server session**, not the client
- client sending `user_id = 'other'` is re-checked against `session.user_id` and rejected

### Q6. Compatibility with existing RAW SQL apps?

- keep current behavior: `allowlist.rawAllowed: true` + `policyMode: "off"`
- gradual migration: adopt DSL → declare policy → per-table `enforce`

## 11. Appendix A — index.html Bootstrap Exposure Analysis (Separate Issue)

### 11.1 Observation

Build output `index.html` embeds ECDH handshake, OPFS cache, and WASM loader bootstrap JS in plaintext.

### 11.2 Risk Assessment

| item | exposed? | actual impact |
| ---- | -------- | ------------- |
| DB credentials / API tokens | ❌ | Opaque Handle pattern — only in Cloudflare env vars |
| session master key | ❌ | runtime ECDH, computed independently on server/client |
| backend business logic | ❌ | inside WASM (QuickJS), not exposed as JS |
| ECDH endpoint path | ⚠️ | `/api/_dokkebi/handshake` observable in HTTP traffic anyway |
| crypto algorithms | ⚠️ | AES-256-GCM / HMAC-SHA256 — public standards, OK per Kerckhoffs |
| build version / hash | ⚠️ | `window.__DOKKEBI_BUILD_VER__` — minor info for attack surface mapping |
| OPFS path / DB filename | ⚠️ | client-side cache — meaningful only in attacker's own browser |

**Conclusion: per Kerckhoffs, exposing algorithms is not a problem. Real secrets (keys, tokens, logic) are not exposed → not a serious security issue.**

### 11.3 Still Worth Hardening (priority order)

1. **Minimize build hash/version exposure**
   - do not put `window.__DOKKEBI_BUILD_VER__` on global `window`; isolate in closure
   - or use meaningless random build ID instead of hash

2. **Disable console.log banner/debug in production**
   - current `console.log('%c 🔮 DOKKEBI ...')` is branding but gives attackers hints
   - add `verboseBootstrap: false` in `dokkebi.config.js`; remove banner/logs on deploy

3. **SRI (Subresource Integrity) for external resources**
   - bootstrap itself is inline → OK for now
   - if `bundle.js`, `dokkebi-qjs.js` move to `<script src>`, SRI required

4. **Tighter CSP**
   - `script-src 'self' 'sha256-<inline script hash>'` to allow only this inline bootstrap
   - remove `'unsafe-inline'` if present (compute bootstrap hash at build time)

5. **Move more sensitive logic into WASM** (see answer ③)
   - move key derivation (HKDF) / HMAC into QuickJS
   - JS glue becomes thin shell: `fetch` + byte passing only
   - Web Crypto API boundary cannot be fully removed (browser constraint)

6. **Minify bootstrap + obfuscate variable names**
   - ① `minify: true` already on bundles — but bootstrap inlined in `index.html` is a separate path
   - add minify option to `injectBootstrapAll()` for production builds

### 11.4 Priority Recommendation

- **High value, low cost (apply soon)**: 1, 2, 6
- **Medium term**: 3, 4 (per-project CSP policies)
- **Long term / large change**: 5 (crypto inside QuickJS — performance tradeoff)

Items 1, 2, 6 from this appendix can be applied quickly separately from Tenant Policy if needed.
